## Характеристика MVC

### Основні компоненти
- **Model**  
  Відповідає за управління даними та бізнес-логікою. Забезпечує зберігання, обробку та валідацію даних.

- **View**  
  Відповідає за відображення інформації користувачу. Забезпечує рендеринг інтерфейсу на основі даних, отриманих з Model.

- **Controller**  
  Виконує роль посередника між Model та View. Обробляє запити користувача, викликає відповідні операції Model та визначає, як представити дані у View.

### Переваги MVC
- **Чітке розділення обов’язків**  
  Забезпечує логічне розділення між бізнес-логікою, представленням даних та управлінням запитами, що спрощує підтримку та розвиток додатку.
  
- **Модульність та масштабованість**  
  Легке розширення системи завдяки незалежності окремих компонентів.

- **Популярність у веб-розробці**  
  Широко використовується у динамічних веб-додатках, що дозволяє ефективно управляти запитами та відображенням інформації.

### Недоліки MVC
- **Складність взаємодії компонентів**  
  У великих проектах може виникати складність у координації між компонентами, що ускладнює налагодження та тестування.
  
- **Обмежена тестованість Controller**  
  Тісна інтеграція з View може впливати на можливості ізольованого модульного тестування.

## Характеристика MVP

### Основні компоненти
- **Model**  
  Виконує ту ж роль, що й у MVC, тобто управляє даними та бізнес-логікою.

- **View**  
  Представляє собою пасивний інтерфейс, який відповідає лише за відображення даних. Не містить логіки обробки подій.

- **Presenter**  
  Виконує роль активного посередника між Model та View. Обробляє всі події користувача, викликає відповідні операції Model та оновлює View. Завдяки цьому Presenter забезпечує повну ізоляцію View від бізнес-логіки.

### Переваги MVP
- **Покращена тестованість**  
  Завдяки ізольованій логіці, що знаходиться в Presenter, можна проводити детальне модульне тестування без взаємодії з UI.

- **Чіткий розподіл відповідальності**  
  View залишається пасивним, що спрощує підтримку та розширення інтерфейсу користувача.

- **Гнучкість реалізації**  
  Легко адаптується для складних інтерфейсів, де важливо тестування логіки взаємодії.

### Недоліки MVP
- **Збільшена архітектурна складність**  
  Для невеликих проектів використання MVP може бути надмірно громіздким через додатковий шар Presenter.

- **Підвищені витрати ресурсів на розробку**  
  Більше компонентів може вимагати додаткових зусиль для розробки та підтримки.

## Порівняння MVC та MVP

| Аспект                      | MVC                                                                                   | MVP                                                                                   |
|-----------------------------|---------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| **Основний проміжний компонент** | **Controller:** Обробляє запити та координує взаємодію між Model та View, з частковою логікою.  | **Presenter:** Активно управляє всіма аспектами взаємодії, ізолюючи View від бізнес-логіки. |
| **Тестованість**            | Може бути ускладненою через тісну інтеграцію View з Controller.                       | Забезпечує кращу модульність та ізоляцію, що сприяє простішому тестуванню.              |
| **Сфера застосування**      | Переважно використовується у веб-додатках для обробки динамічного контенту.             | Частіше застосовується у десктопних та мобільних додатках, де критична тестованість.    |
| **Архітектурна складність** | Простий у реалізації для невеликих проектів, але може стати складним при масштабуванні.   | Більш структуровано розділяє відповідальності, але може бути надмірним для простих рішень. |

## Висновок
Обидва патерни мають за мету забезпечити розділення обов’язків та підвищити підтримуваність коду, проте підходять до цього завдання різними способами.  
- **MVC** є ефективним для динамічних веб-додатків завдяки простоті реалізації та швидкому управлінню запитами.  
- **MVP** забезпечує більш високу тестованість та ізоляцію логіки взаємодії, що робить його ідеальним для проектів, де критична якість тестування та масштабованість інтерфейсу.
